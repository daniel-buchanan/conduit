# Nested member-access chains are null-safe when compiled

`PropertyNameExtractor.ExtractAndCompile` compiled a `Should()` expression straight from `expression.Compile()`, with no null-guarding along the way. `Extract` already requires the expression to be a pure member-access chain rooted at the lambda parameter (e.g. `x => x.Address.City`), throwing `ArgumentException` for anything else — but it says nothing about what happens at runtime if an intermediate in that chain, like `Address`, is itself null. Rules always run all of them regardless of an earlier rule's outcome (there's no short-circuiting between rules — see ADR-0002's sibling decision on flat stage execution), so a common pair of rules like "`Address` must not be null" plus "`Address.City` must not be null" crashed the whole validation with an unhandled `NullReferenceException` on the second rule whenever `Address` actually was null, even though the first rule correctly reported it.

We make the compiled delegate null-safe: it now catches `NullReferenceException` and returns `default(TProperty)`, so a null intermediate anywhere in the chain evaluates the same as the leaf property itself being null. This is a broad `catch` deliberately — `Extract`'s own guard guarantees the expression is nothing but member accesses, so a null intermediate is the only possible source of an NRE from invoking the compiled delegate; there's no arbitrary user code in the chain to accidentally swallow an unrelated bug from.

We rejected raising a distinct "path not evaluable" error instead of reusing the leaf-is-null semantics: it would mean every rule (`Null`, `EqualTo`, `In`, `NullOrWhitespace`, ...) needs its own answer for what a broken path means for that specific condition, when "the value here is null" already composes correctly with all of them.
