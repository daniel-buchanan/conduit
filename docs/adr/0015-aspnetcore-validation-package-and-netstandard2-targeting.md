# ASP.NET Core validation integration moves to conduit.aspnetcore.validation; core packages multi-target netstandard2.0

`conduit.validation` pulled in `Microsoft.AspNetCore.Hosting.Abstractions`, `Microsoft.AspNetCore.Mvc.Abstractions`, and `Microsoft.AspNetCore.Mvc.Core` — all pinned at `2.3.9`, a pre-.NET-Core-3 version mismatched against the repo's `net10.0` target — solely to compile three files: `ApplicationBuilderExtensions` (the `AddConduitValidation()` middleware registration), `ConduitValidationExceptionHandler` (the actual middleware, converting `ValidationFailedException`/`StageFailedException`/`ValidatorNotFoundException` into `ProblemDetails` responses), and `ValidationErrorsExtensions` (`ValidationError[] → ModelStateDictionary`). Every other type in `conduit.validation` — `ModelValidator`, `RuleBuilder`, `ValidationStage`, the `Should*Builder` family — has nothing to do with HTTP. A console app, worker service, or queue handler that wanted `conduit.validation`'s actual validation machinery had no way to get it without also pulling in ASP.NET Core.

We moved those three files (and their tests) into a new package, `conduit.aspnetcore.validation`, which references `conduit`, `conduit.validation`, and `conduit.logging`, and depends on ASP.NET Core via `<FrameworkReference Include="Microsoft.AspNetCore.App" />` rather than the old individual packages. `conduit.validation` no longer references AspNetCore in any form. We did not create an empty umbrella `conduit.aspnetcore` package alongside it — nothing generic (non-validation-specific) exists yet to put in one, and building it speculatively would be exactly the kind of hypothetical-future-need scaffolding this repo's own conventions reject.

Splitting the assembly boundary only matters if the result is actually installable separately, so the same change adds real NuGet packaging metadata — `PackageId`, `Description`, `Version` (`0.1.0`, independent per package), with `Authors`/`PackageLicenseExpression`/`PackageProjectUrl`/`RepositoryUrl` centralized in `Directory.Build.props` — to all five library packages. None of them had ever shipped a package before this change (no `PackageId` existed anywhere in the repo), so this is additive, not a version bump. Publishing automation (CI pushing to a feed) is deliberately out of scope; it's a separate, already-tracked gap (`ROADMAP.md` §6, no CI exists at all yet). This change only makes `dotnet pack` produce a correct `.nupkg` per project.

Separately, `conduit`, `conduit.common`, `conduit.logging`, and `conduit.validation` now multi-target `netstandard2.0;net10.0` (previously `net10.0` only), so a consumer isn't forced onto the newest runtime just to reference Conduit's core packages. `conduit.aspnetcore.validation` stays `net10.0`-only: `Microsoft.AspNetCore.App` only resolves against an actual .NET Core TFM, and the only netstandard2.0-compatible path to ASP.NET Core types is the same EOL `2.3.9`-era package line this change removes — reintroducing it to hit netstandard2.0 would be a supply-chain downgrade, not a win. `conduit.tests`/`conduit.benchmarks` also stay `net10.0`-only; netstandard2.0 is a compile target, not something a test runner or benchmark host can execute directly.

Multi-targeting surfaced several BCL gaps, fixed as follows:

- **`init`-only properties and records** (`StdIo.cs`, `ValidationResult.cs`, `StageMetric`, `DebugResult`, `ConduitValidationConfiguration`) need `System.Runtime.CompilerServices.IsExternalInit`, absent from netstandard2.0. Each affected project gets its own `internal` polyfill of that type, compiled only under `#if NETSTANDARD2_0`. This is safe to duplicate per-assembly: the compiler only needs the type to exist in the compilation, never across assembly boundaries.
- **`SHA512.HashData`** (net5+), **`Dictionary<,>.GetValueOrDefault`** (netstandard2.1+), and **`ArgumentNullException.ThrowIfNull`** (net6+) have behavior-identical replacements available on every targeted TFM (`SHA512.Create().ComputeHash(...)`, `TryGetValue`, a manual null check) — applied unconditionally, no `#if` needed, since the replacement isn't TFM-specific.
- **`Task.WaitAsync`** (net6+) has no netstandard2.0 equivalent, and a correct polyfill means hand-reimplementing its cancellation-race semantics — real logic, not a marker type. `conduit.tests` is `net10.0`-only, and project-reference resolution always binds a multi-targeted project's `net10.0` output when referenced from a `net10.0` test project, so a netstandard2.0-only code path can never actually be *executed* here, only compiled. Rather than ship a hand-rolled concurrency primitive with zero real test execution, the netstandard2.0 leg of `AsyncExtensions.Await`/`Await<T>` uses `cancellationToken.ThrowIfCancellationRequested()` followed by a plain synchronous `GetAwaiter().GetResult()`. This is behavior-identical to today for every actual caller: every call site in this codebase (`ModelValidator.Validate`, `Rule.Validate`) passes `CancellationToken.None`, and the existing test coverage (`AsyncExtensionsTests`) only asserts exception-unwrapping, never cancellation. The netstandard2.0 leg simply doesn't preempt mid-wait on a token nothing here passes.

`LangVersion` also drops from `preview` to `latest`, centralized into `Directory.Build.props` alongside `Nullable`/`ImplicitUsings` (previously hand-duplicated identically across every `.csproj`). The build stayed clean on the first attempt, confirming nothing shipped actually depended on a preview-only language feature.

No compatibility shim and no `!` breaking-change marker: nothing has ever been published as a NuGet package before this change, so there is no external semver contract to break. This is the first release-shaped state of these packages, not a break from a prior one.
