# Configuration interfaces expose their real surface directly; no cross-assembly downcasts

`conduit.validation` needed to mutate state on `conduit`'s configuration builders — add a service descriptor, register a default stage, exclude a pipe from validation — but `IConduitConfigurationBuilder` and `IConduitPipeBuilder<TRequest, TResponse>` never declared those members. `conduit.validation`'s extension methods worked around this by reaching past the interface to the one concrete implementation: `ConfigurationBuilderExtensions.AddValidation` did `var conduitBuilder = builder as ConduitConfigurationBuilder;` and then called through it with an unchecked `!` (an `NullReferenceException` waiting for any other implementation of the interface), and `ConduitPipeBuilderExtensions.ExcludeValidation` did `if (self is ConduitPipeBuilder<TRequest, TResponse> builder) builder.ExcludeFromValidation();` with a silent no-op otherwise — calling `ExcludeValidation()` could look like it worked while quietly leaving validation switched on.

Both casts only ever succeeded because there is exactly one implementation of each interface today. That made the interfaces a fiction: the real contract callers depended on was the concrete class, not the abstraction `conduit.validation` was declared against.

We add the missing members directly to the interfaces instead: `IConduitConfigurationBuilder` gains `AddDescriptor`, `AddDefaultPreExecutionStage`, and `AddDefaultPostExecutionStage`; `IConduitPipeBuilder<TRequest, TResponse>` gains `ExcludeValidation()`. Both concepts already belonged to `conduit` core, not to validation specifically — `PipeDescriptor.ExcludeValidation` and the `IValidationPipeStage` marker interface already lived in `conduit` (see [ADR-0002](0002-flat-sequential-stage-execution.md)'s sibling stage machinery) precisely so core wouldn't need to reference the validation package. Only the builder interfaces had lagged behind the concrete classes. `conduit.validation` now calls these members directly; the unsafe downcasts are gone. `ConduitPipeBuilderExtensions.WithValidation` is unaffected — it only ever went through `AddStage<TStage>()`, a real interface member.

This surfaced a second gap in the same area: `RegisterHandler` (the simple registration path, building its stage list via `DefaultPipeConfiguration<TRequest, TResponse, THandler>.GetStages()`) had no way to exclude validation at all, unlike `RegisterPipe` (built via `PipeFactory`, which already filtered `IValidationPipeStage` stages when asked). `RegisterHandler` now takes an optional `Action<IHandlerRegistrationOptions>? configure` with a single `ExcludeValidation()` method, and `DefaultPipeConfiguration<TRequest, TResponse, THandler>` filters its stage list the same way `PipeFactory` does. `RegisterHandler` stays deliberately narrower than `RegisterPipe` — no `AddStage`, no custom stage ordering — this only brings the one existing cross-cutting knob to parity.
