# Unexpected stage exceptions get wrapped as StageFailedException

`Pipe.ExecuteStage`'s catch block currently rethrows any exception from a stage, rule, or validator raw (`throw;`), so callers behind `ConduitValidationExceptionHandler` see whatever the failing code happened to throw instead of a stable Conduit-level contract. `StageResult.WithException` already models a failed stage carrying an exception, but nothing constructed it — the constructor was dead code.

We now catch unexpected exceptions in `ExecuteStage` and wrap them as `StageFailedException` via `StageResult.WithException`, so `HandleUnsuccessfulResult` raises a consistent, catchable type for anything a stage didn't itself validate against. Three exception types are deliberately exempted and continue to pass through unwrapped, because they are already Conduit's own stable, expected-failure types: `ValidationFailedException`, `StageFailedException` itself (avoids double-wrapping), and `ValidatorNotFoundException`. `ValidatorNotFoundException` (thrown by `ValidationStage` when `ThrowIfValidatorNotFound()` is configured and no validator resolves) is also added to `ConduitValidationExceptionHandler`'s `KnownExceptionHandlers`, so a missing validator produces its own distinct ProblemDetails response rather than surfacing as a generic "pipeline stage failed" 500.

`ValidatorNotFoundException` lives in `conduit.validation`, which `conduit` core must never reference (see [ADR-0007](0007-configuration-interfaces-own-their-real-surface.md)), so `ExecuteStage`'s catch block can't type-check against it directly. We add a marker interface, `IPassthroughException` (in `conduit.Exceptions`), for exactly this: `ValidationFailedException` and `StageFailedException` implement it directly (core types, no boundary issue), and `ValidatorNotFoundException` implements it from `conduit.validation` — the same marker-interface pattern `IValidationPipeStage` already uses to let core recognize a validation-package concept without referencing the package.
