# `AsyncExtensions.Await` no longer wraps exceptions in `AggregateException`

`Await`/`Await<T>` called `Task.Wait(cancellationToken)` and `Task<T>.Result` to synchronously bridge an async call — the mechanism `ModelValidator.Validate()` and `Rule.Validate()` use to expose a synchronous API over their real async implementation. Both `Task.Wait` and `Task<T>.Result` wrap a faulted task's exception in `AggregateException`, so any exception thrown inside a rule or validator (a null-values guard, a bug in a hand-written rule, anything) reached a synchronous caller as `AggregateException` instead of its real type. `ConduitValidationExceptionHandler`'s known-exception matching (`ex is ValidationFailedException`, etc.) and any consumer catching a specific exception type both silently stopped working the moment code went through the synchronous path instead of the async one, with no visible symptom other than the wrong catch block missing.

We changed both methods to `task.WaitAsync(cancellationToken).GetAwaiter().GetResult()`. `GetAwaiter().GetResult()` (what `await` itself compiles down to) unwraps a single faulting exception and rethrows it directly, preserving its original type and stack trace, instead of wrapping it; `WaitAsync(cancellationToken)` keeps the original cancellation-observing behavior of `Wait(cancellationToken)`, so a caller passing a token still gets it honored on the blocking wait. This makes the synchronous and asynchronous validation entry points behave identically for exception types, closing a gap this repo's edge-case review turned up (a `NullReferenceException` and later an `ArgumentNullException` both surfacing as `AggregateException` only through `Validate()`, never through `ValidateAsync()`).
