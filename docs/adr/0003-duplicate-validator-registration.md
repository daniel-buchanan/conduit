# Scan-vs-scan validator collisions throw; explicit registration always wins

`ValidationBuilder.WithValidatorsFromAssembly` can discover two or more `ModelValidator<TRequest, TResponse>` implementations for the same `(TRequest, TResponse)` pair, either in one scan or across multiple scans, and today silently keeps only the last one registered. `RegisterPipe` already guards against this class of mistake for pipes via `PipeAlreadyRegisteredException`; validator registration had no equivalent.

We introduce `ValidatorAlreadyRegisteredException` (mirroring `PipeAlreadyRegisteredException`) and throw it only when two assembly-scan discoveries collide on the same `(TRequest, TResponse)` pair — this is almost always an accidental duplicate class, not a deliberate choice. An explicit `WithValidatorFor` call (instance- or type-based) is always allowed to register over an existing entry for that pair, regardless of whether the existing entry came from a scan or another explicit call, and never throws: calling it is a deliberate, last-registered-wins override. This keeps scans safe-by-default while leaving an escape hatch for consumers who need to override a scanned validator without editing the scanned assembly.

Implemented in `ValidationBuilder.WithValidatorsFromAssembly`, which tracks every `(TRequest, TResponse)` pair a scan has discovered (across calls) and throws `ValidatorAlreadyRegisteredException` on a repeat. `WithValidatorFor` never consults that tracking, so it always overrides. One consequence worth knowing: a scan walks every type in the target assembly, so any two `ModelValidator<TRequest, TResponse>` classes for the same pair collide even if they're unrelated test fixtures never meant to be scanned — see `conduit.tests/Validation/ModelValidatorTests.cs` and `PropertyNameExtractionTests.cs`, where standalone rule fixtures were each given a distinct request type for exactly this reason.
